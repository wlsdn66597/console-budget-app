# Windows 실행 증빙 — 평가 항목 1 (세부 1~7)

이 문서는 Windows 명령 프롬프트(cmd)에서 `python3 -m budget_app`을 실제로 실행한 결과를 평가 항목별로 정리한 것입니다. 모든 명령은 저장 폴더(`./data`)가 없는 깨끗한 상태에서 시작했습니다. 각 캡처 아래에 명령이 무엇을 확인하는지와 결과가 무엇을 뜻하는지 설명했습니다.

## 한눈에 보기

| 항목 | 확인 대상 | 결과 |
|---|---|---|
| 1 | import / add / list / search / update / delete / export 동작 | 정상 |
| 2 | 프로그램 재실행 후 거래·카테고리·예산 데이터 유지(저장 파일 3개 이상) | 정상 |
| 3 | category add / list / remove, 사용 중인 카테고리 삭제 처리 | 정상 |
| 4 | budget set 저장, summary의 예산 사용률·초과 경고 | 정상 |
| 5 | import/export CSV 스키마(UTF-8, 헤더, 컬럼) | 정상 |
| 6 | 잘못된 입력·파일에 대한 오류 메시지와 해결 힌트(스택트레이스 없음) | 정상 |
| 7 | 오류 상황의 0이 아닌 종료 코드와 실행 로그 기록 | 정상 |

## 1. 거래 명령 동작 (import / add / list / search / update / delete / export)

![거래 명령 동작 확인](evidence/01-transaction-commands.png)

### 실행한 확인

- `import --from samples/import_sample.csv`로 샘플 CSV의 거래를 일괄 등록했습니다.
- `add`로 거래 1건을 대화형으로 입력했습니다(날짜 → 타입 → 카테고리 → 금액 → 메모 → 태그 순서).
- `list --limit 3`으로 최근 3건을 조회했습니다.
- `search`로 두 가지 조건을 검색했습니다. 하나는 카테고리와 타입, 다른 하나는 기간·메모 키워드·태그를 함께 지정했습니다.
- `update --id TX-000003`으로 금액·메모·태그를 수정하고, `delete --id TX-000004`로 거래 1건을 삭제한 뒤 `list`로 전체 목록을 다시 확인했습니다.
- `export --out export.csv --month 2024-01`로 2024년 1월 거래를 CSV로 내보냈습니다.

### 결과 설명

**import**: 처음 실행할 때 `./data` 폴더가 없었으므로 `[안내] 저장 폴더를 초기화했습니다`가 출력되고 기본 카테고리 5개가 생성됐습니다. 샘플 CSV 6행 중 7번째 줄은 등록되지 않은 카테고리 `unknown`을 써서 `[건너뜀]` 처리됐습니다. 나머지 5행은 정상 등록되어 `imported=5, skipped=1`이 출력됐습니다. 잘못된 행 하나 때문에 전체 가져오기가 실패하지 않고, 정상 행만 저장한 뒤 건너뛴 이유를 행 번호와 함께 보여줍니다.

**add**: 입력이 끝나자 `[저장 완료] id=TX-000006`이 출력됐습니다. import로 TX-000001~000005가 이미 있으므로 다음 번호가 이어서 발급됐습니다.

**list**: `--limit 3`을 주자 날짜 기준 최신순으로 3건만 출력됐습니다. 가장 최근 날짜인 TX-000006(2026-10-11)이 맨 위에 있습니다.

**search**:
- `--category food --type expense`는 식비 지출인 TX-000006, 000005, 000003만 출력했습니다. 교통(TX-000004), 월세(TX-000002), 수입(TX-000001)은 제외됐습니다.
- `--from 2024-01-01 --to 2024-01-10 --q 회식 --tag team`은 네 조건을 모두 만족하는 TX-000005 한 건만 출력했습니다. 조건을 함께 지정하면 모든 조건을 동시에 만족하는 거래만 검색된다는 것을 확인했습니다.

**update**: TX-000003의 금액이 `12000 → 13000`, 메모가 `점심 → 점심(수정)`, 태그가 `#meal → #meal #lunch`로 바뀌었습니다. 지정하지 않은 날짜·타입·카테고리는 그대로입니다. 즉 옵션으로 준 필드만 수정됩니다.

**delete**: `[삭제 완료] id=TX-000004` 이후 전체 `list`에서 TX-000004가 사라졌습니다. 나머지 거래의 id는 다시 매겨지지 않고 그대로 유지됩니다.

**export**: `export.csv (4 records)`가 출력됐습니다. 2024년 1월 거래는 TX-000001, 000002, 000003, 000005의 4건입니다. add로 넣은 TX-000006은 날짜가 2026-10-11이라 대상이 아니므로 4건이 맞습니다.

### 실행한 확인

1번 작업을 마친 후 명령 프롬프트 창을 닫았습니다. 그다음 새 창을 열어(`Microsoft Windows [Version ...]` 시작 화면) 프로젝트 폴더로 이동하고 `list`를 실행했습니다.

### 결과 설명

새로 연 터미널에서도 1번에서 저장한 거래 5건이 그대로 출력됩니다. 단순히 데이터가 남아 있는 것만이 아니라, 수정한 내용과 삭제 결과도 함께 유지됐습니다.

- TX-000003은 수정된 값(`13000`, `점심(수정)`, `#meal #lunch`)으로 남아 있습니다.
- 삭제한 TX-000004는 다시 나타나지 않습니다.

프로그램은 데이터를 메모리가 아닌 `./data` 폴더의 JSONL 파일(UTF-8, 한 줄에 JSON 하나)에 저장합니다.

| 파일 | 내용 |
|---|---|
| `transactions.jsonl` | 거래 내역 |
| `categories.jsonl` | 카테고리 목록 |
| `budgets.jsonl` | 월 예산 |
| `app.log` | 명령 실행 로그(명령명, 종료 코드, 실행 시간) |

update와 delete는 원본 파일을 한 줄씩 읽으면서 임시 파일에 전체를 다시 쓰고, 마지막에 `os.replace`로 원본과 교체합니다. 그래서 쓰는 도중 오류가 나도 원본 파일은 깨지지 않습니다.

## 3. 카테고리 관리 (사용 중인 카테고리 삭제 처리 포함)

![카테고리 추가·조회·삭제 확인](evidence/03-category.png)

### 실행한 확인

- `category list`로 기본 카테고리를 확인했습니다.
- 사용하지 않는 카테고리 `hobby`를 추가한 뒤 바로 삭제했습니다.
- 거래에서 사용 중인 `food`를 삭제해 봤습니다.
- 대체 카테고리 `dining`을 추가하고 `category remove --name food --replace dining`으로 거래를 옮긴 뒤 삭제했습니다.
- `category list`와 `list`로 결과를 확인했습니다.

### 결과 설명

**기본 카테고리**: 카테고리 파일이 비어 있으면 `food, transport, rent, salary, etc` 5개가 자동 생성됩니다.

**사용하지 않는 카테고리**: `hobby`는 이를 쓰는 거래가 없으므로 `[저장 완료]` 뒤 곧바로 `[삭제 완료]`됐습니다.

**사용 중인 카테고리**: `food`는 거래 3건(TX-000003, 000005, 000006)이 사용 중이므로 삭제가 거부됐습니다. 출력은 다음과 같습니다.

```
[오류] 'food' 카테고리를 사용하는 거래가 3건 있어 삭제할 수 없습니다.
[힌트] `category remove --name food --replace <대체카테고리>`로 옮긴 뒤 삭제하세요.
```

카테고리를 그냥 지우면 거래가 존재하지 않는 카테고리를 가리키게 됩니다. 이를 막으려고 삭제를 거부하고, 해결 방법을 힌트로 알려줍니다. 스택트레이스 없이 원인과 해결책만 출력됩니다.

**대체 후 삭제**: `--replace dining`을 지정하자 `[삭제 완료] category=food (거래 3건을 'dining'로 이동)`이 출력됐습니다. 그 결과는 다음과 같습니다.

- `category list`에서 `food`가 사라지고 `dining`이 추가됐습니다.
- `list`에서 식비 거래 3건(TX-000006, 000005, 000003)의 카테고리가 `dining`으로 바뀌었습니다.
- 다른 카테고리의 거래(rent, salary)는 바뀌지 않았습니다.

거래 이동도 update/delete와 같은 방식(임시 파일 작성 후 `os.replace` 교체)으로 처리하므로, 중간에 실패해도 데이터가 반쯤 바뀐 상태로 남지 않습니다.

## 4. 월 예산 저장과 summary 사용률·초과 경고

![예산 이내 summary 확인](evidence/04a-budget-within.png)

![예산 초과 summary 확인](evidence/04b-budget-over.png)

### 실행한 확인

- `budget set --month 2024-01 --amount 200000`으로 예산을 저장하고 `budget show`로 조회했습니다.
- 이어서 `summary --month 2024-01`을 실행했습니다.
- 다음으로 예산을 `150000`으로 다시 설정하고 같은 summary를 실행했습니다.
- 마지막으로 `budget show`로 저장된 값을 다시 확인했습니다.

### 결과 설명

2024년 1월 총지출은 196,000원입니다. 월세 150,000원과 식비(dining) 46,000원(13,000 + 33,000)을 더한 값입니다. 2026-10-11 거래는 이 달에 포함되지 않습니다.

| 예산 | 사용률 | 초과 경고 |
|---|---|---|
| 200,000원 | 196,000 / 200,000 = `98.0%` | 없음 |
| 150,000원 | 196,000 / 150,000 = `130.7%` | `[경고] 예산을 46000원 초과했습니다!` |

- 예산 이내일 때는 사용률만 출력하고, 지출이 예산을 넘을 때만 초과 금액(196,000 − 150,000 = 46,000원)과 함께 경고를 출력합니다.
- 같은 달에 예산을 다시 설정하면 기존 값을 덮어씁니다. 두 번째 `budget show`에 `2024-01: 150000원` 한 줄만 나오는 것으로 확인됩니다. 예산은 `budgets.jsonl`에 월별로 한 줄씩 저장됩니다.
- summary는 총수입·총지출·잔액(3,000,000 − 196,000 = 2,804,000원)도 함께 보여줍니다. 지출 TOP N 목록도 출력하는데, 기본값은 3이지만 이 달의 지출 카테고리가 rent와 dining 두 개뿐이라 `지출 TOP 2`로 출력됐습니다.

## 5. import/export CSV 스키마

![CSV 스키마 확인](evidence/05-csv-schema.png)

### 실행한 확인

- `chcp 65001`로 명령 프롬프트의 코드페이지를 UTF-8로 바꿨습니다.
- `type`으로 export 결과 파일(`export.csv`)과 import 샘플 파일(`samples\import_sample.csv`)을 출력했습니다.
- Python으로 `export.csv`를 UTF-8로 읽어 디코딩 오류가 없는지 확인했습니다.
- `--from/--to` 기간 조건으로 한 번 더 export했습니다.

### 결과 설명

**헤더와 컬럼**: 두 파일 모두 첫 줄이 `date,type,category,amount,memo,tags`로 같습니다. 그래서 export한 파일을 그대로 다시 import할 수 있습니다. id는 CSV에 넣지 않으며, import할 때 새로 발급됩니다.

| column | 형식 | 캡처에서 확인한 값 |
|---|---|---|
| date | YYYY-MM-DD | `2024-01-05` |
| type | income / expense | `income`, `expense` |
| category | 등록된 카테고리 | `salary`, `rent`, `food` |
| amount | 양수 정수 | `13000` |
| memo | 문자열(선택) | `점심(수정)` |
| tags | 쉼표 구분 문자열(선택) | `"meal,lunch"` |

**태그 표기**: 태그가 여러 개이면 `"house,fixed"`처럼 큰따옴표로 감싸서, 컬럼 구분자인 쉼표와 섞이지 않게 합니다. 태그가 하나이면 `meal`처럼 따옴표 없이 기록됩니다. 태그가 없으면 `1월 월급,`처럼 마지막 칸이 비어 있습니다.

**UTF-8**: 한글 메모(`월세`, `저녁 회식`)가 깨지지 않고 출력되며, `UTF-8 decode OK`가 출력됩니다. 따라서 파일이 UTF-8로 저장됐음을 확인할 수 있습니다. import는 Excel이 붙이는 BOM이 있는 UTF-8 파일도 받습니다.

**export의 category가 food인 이유**: `export.csv`는 1번 단계에서 만들었고, 3번에서 food를 dining으로 바꾸기 전입니다. 그래서 그 시점의 카테고리 `food`가 그대로 기록돼 있습니다.

**기간 조건**: `--from 2024-01-01 --to 2026-12-31`로 내보내자 `5 records`가 출력됐습니다. `--month 2024-01`의 4건에 2026-10-11 거래 1건이 더해진 결과입니다. 월 단위와 기간 단위 조건이 모두 동작합니다.

## 6. 잘못된 입력과 파일 오류 처리

![오류 메시지와 힌트 확인](evidence/06-error-handling.png)

### 실행한 확인

- 존재하지 않는 id로 `update`와 `delete`를 실행했습니다.
- 기간 조건 없이 `export`를 실행했습니다.
- 없는 파일, 필수 헤더가 없는 CSV(`bad_header.csv`), 일부 행이 잘못된 CSV(`bad_rows.csv`)를 각각 import했습니다.
- `add`에서 날짜·타입·금액을 일부러 잘못 입력했습니다.

### 결과 설명

모든 오류는 Python 스택트레이스(`Traceback ...`) 없이 `[오류] 원인`과 `[힌트] 해결 방법` 두 줄로만 출력됩니다.

| 상황 | 오류 | 힌트 |
|---|---|---|
| 없는 id 수정/삭제 | `id=TX-999999 거래가 없습니다.` | `list` 또는 `search`로 id 확인 |
| 기간 없는 export | `export에는 기간 조건이 필요합니다.` | `--month` 또는 `--from/--to` 지정 |
| 없는 파일 import | `파일을 찾을 수 없습니다: nofile.csv` | 경로 확인 |
| 헤더 불량 CSV | `CSV 헤더에 필수 컬럼이 없습니다: date, type, category, amount` | 올바른 헤더 예시 제시 |

**일부 행만 잘못된 CSV**: 파일 전체를 거부하지 않고 행 단위로 검증했습니다.

- 2행: 존재하지 않는 날짜 `2024-02-30` → 건너뜀
- 3행: 허용되지 않은 타입 `spend` → 건너뜀
- 4행: 음수 금액 `-5` → 건너뜀
- 5행: 정상 → 저장(TX-000007)

결과는 `imported=1, skipped=3`입니다. 잘못된 행 때문에 정상 데이터까지 버려지지 않고, 어떤 행이 왜 빠졌는지 행 번호로 알려주므로 사용자가 원본 CSV를 고칠 수 있습니다.

**대화형 입력 오류**: `add`에서 날짜 `2026/10/11`과 `xxx`, 타입 `xx`, 금액 `ff`를 입력할 때마다 오류와 힌트가 출력됐습니다. 프로그램이 종료되지 않고 **같은 질문을 다시** 물었으며, 올바른 값을 입력하자 다음 단계로 넘어가 `[저장 완료] id=TX-000008`로 끝났습니다. 잘못 입력해도 처음부터 다시 할 필요가 없습니다.

## 7. 오류 상황의 종료 코드와 실행 로그

### 실행한 확인

명령을 실행한 직후 `echo exit=%ERRORLEVEL%`로 종료 코드를 확인했습니다. 마지막으로 PowerShell `Get-Content -Tail 8`로 `data\app.log`의 최근 기록을 조회했습니다.

cmd에서 `명령 & echo %ERRORLEVEL%`처럼 한 줄로 이어 쓰면, `%ERRORLEVEL%`이 명령 실행 전에 치환돼 이전 값이 출력됩니다. 그래서 명령과 echo를 각각 따로 실행했습니다.

### 결과 설명

| 상황 | 종료 코드 | 의미 |
|---|---|---|
| `list` 정상 실행 | `0` | 성공 |
| `delete --id TX-999999` | `1` | 처리 중 오류(없는 id) |
| `list --limit 0` | usage 출력 | argparse 인자 오류(코드 2) |
| `add` 도중 Ctrl+C | `130` | 사용자 입력 중단 |

- 오류 상황에서는 종료 코드가 0이 아니므로, 스크립트나 CI에서 성공과 실패를 구분할 수 있습니다.
- 처리 중 오류(1), 인자 오류(2), 사용자 중단(130)도 서로 다른 값으로 구분됩니다.
- Ctrl+C로 중단해도 스택트레이스 대신 `[중단] 입력이 취소되었습니다.`만 출력됩니다.

**list 결과**: 정상 실행한 `list`에서 같은 날짜(2026-10-11)의 TX-000008과 TX-000006은 나중에 생성된 TX-000008이 먼저 나옵니다. 6번에서 import한 TX-000007(2024-02-03)은 날짜 순서에 맞는 위치에 있습니다.

**app.log**: 모든 명령 핸들러에 공통 데코레이터(`@log_execution`)가 적용돼 있어, 실행마다 시각, 명령명, 종료 코드, 실행 시간이 한 줄씩 기록됩니다.

- 6번의 export 실패(`exit=1`), import 실패 두 번(`exit=1`)과 부분 성공(`exit=0`)이 기록돼 있습니다.
- 7번의 `delete exit=1`, `add exit=130`도 기록돼 있습니다.
- `add`의 `elapsed=71432.9ms`는 사용자가 값을 입력하며 기다린 시간이 포함된 값입니다.
- `list --limit 0`은 인자 해석 단계(argparse)에서 핸들러가 실행되기 전에 끝나므로 로그에 남지 않습니다.

## 최종 확인

평가 항목 1의 세부 요구사항 7개를 모두 실제 실행으로 확인했습니다. 확인한 내용은 다음과 같습니다.

- 거래 명령(add/list/search/summary/export/import/update/delete)
- 재실행 후 데이터 유지
- 카테고리 관리와 사용 중인 카테고리 처리
- 예산 사용률과 초과 경고
- CSV 스키마
- 스택트레이스 없는 오류 메시지와 힌트
- 0이 아닌 종료 코드

모두 Windows 명령 프롬프트 환경에서 정상 동작합니다.
